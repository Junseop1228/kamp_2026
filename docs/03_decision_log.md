## D-002. 복수 데이터셋 결합을 전략 전제에서 제외

- **일자** 2026-08-28
- **상태** 확정 (D-002a 가설 폐기에 따름)
- **결정** 복수 제조AI데이터셋을 결합하는 접근을 전략 전제에서 뺀다. 분석·연습·제출은 단일 데이터셋 안에서 2단 이상을 엮는 형태로 설계한다.
- **배경** 카탈로그 수집(WO-001) 중 동일 설비 데이터가 분석목적별로 분리 등재된 쌍을 발견했다(no.47/48 열처리 — 주 데이터 row 2,939,722 일치, no.49/50 의류 — 레코드·용량 일치). 여기서 "결합하면 데이터 활용도 점수에 유리하다"는 가설을 세웠다(D-002a).
- **폐기 근거** 과거 4회 과제공개 원문을 대조한 결과 정반대였다.
  - 제2~4회 — 데이터셋을 단수로 지정 ("용해탱크 제조AI데이터셋" 등)
  - 제5회 — "팀별 **1종**의 제조AI데이터셋을 선택하여 제조AI 분석"으로 명시
  - 진출작 34팀 제목에 복수 데이터셋 사용 사례 없음. 전부 단일 데이터셋 내 다단 구조
  즉 결합은 유리한 전략이 아니라 규정 위반이었다.
- **혼동의 정체** "단일 모델 제출 금지" 원칙은 **모델 단계가 2개 이상**이라는 뜻인데, 이를 **데이터셋이 2개 이상**으로 바꿔 읽었다. "예측 + 원인분석"은 단일 데이터셋으로 성립한다.
- **제6회 문구 해석** 공고문 "50종 중 1종 또는 여러 종을 활용하여 문제 출제 예정"의 주어는 출제자다. 참가팀 재량이 아니다. 출제자가 실제로 여러 종을 묶어 낼 가능성은 남아 있으나, 그 경우 결합은 강제되는 것이지 우리가 선택하는 것이 아니다. 9/21 과제공개에서 확인한다.
- **감수한 리스크** 제6회가 실제로 복수 데이터셋 과제로 나올 경우 결합 경험이 없는 상태로 진입한다. 다만 데이터셋 **내부** 다중파일 처리(no.36의 정상/이상 분리 등)는 Sprint 1에서 그대로 겪으므로, 조인 자체가 미경험 영역이 되지는 않는다.
- **재검토 시점** 2026-09-21 과제공개 수령 직후

## D-003. Sprint 1 대상을 no.36 소성가공 품질보증으로 확정

- **일자** 2026-08-28
- **상태** 확정
- **결정** Sprint 1(9/1~9/7) 연습 대상을 `no.36 소성가공 품질보증 AI 데이터셋` 단독으로 한다.
- **배경** D-002로 결합 전제가 빠지면서 후보 재산정이 필요했다.
- **선정 기준** ①단일 데이터셋 안에서 2단 이상 설계 가능 ②7일 안에 문서까지 도달하는 회전속도 ③결과의 타당성을 대조할 기준선 존재 ④도메인 담당의 투입 여지
- **선정 이유**
  1. **제5회 선택지 ② 그 자체다.** 실제로 출제된 문제를 그대로 푸는 것이 리허설 정의에 가장 가깝다. 진출작이 기준선이 된다
  2. **1.61MB로 후보 중 가장 가볍다.** 리허설의 목적은 파이프라인 결함 노출인데, 대용량이면 파이프라인이 아니라 I/O를 디버깅하게 된다
  3. **압출성형기 변수(수지온도·압력·모터속도)가 화공 도메인에 직접 닿는다.** 물리 기반 파생변수 설계가 실제로 산출될 수 있는 축이며, 이는 정성 배점 30점(제조현장 문제 이해도 + 제조AI데이터셋 이해도 + 결과해석 우수성)에 대응한다
  4. 라벨(양/불량)이 명시돼 있어 지도학습 파이프라인 전 구간이 첫날부터 돌아간다
- **대안과 기각 사유**
  - `no.40 주조 공정최적화`(8.18MB) — 제4회 진출작 10팀으로 기준선이 가장 두껍다. 다만 2026.07.13 수정본이라 진출작과 데이터가 다를 수 있고, 다이캐스팅은 화공보다 재료·주조 도메인이라 도메인 투입 효율이 떨어져 기각
  - `no.48 열처리 공정최적화`(481MB) — 구조는 가장 실제적이나 7일 내 문서 도달 불가로 기각. 6절에 보류 항목으로 남겨 로딩 시간 실측만 시도
  - `no.35 소성가공 예지보전`과의 병행 — 설비가 다르므로(유압펌프 모터 대 압출성형기) 결합 대상이 아니다. 보조 트랙으로만 둔다
- **감수한 리스크**
  1. 소규모 데이터라 대용량 처리에서 드러나는 결함(메모리, 청크 로딩)을 Sprint 1에서 못 잡는다 → 보류 항목의 481MB 로딩 실측으로 부분 보완
  2. 제5회 대상이라 제6회 재출제 가능성이 낮다. 연습 내용이 그대로 재사용되지는 않는다 → 애초에 이전되는 것은 코드 모듈과 프로토콜이지 특정 데이터 분석 결과가 아니다
- **재검토 시점** Sprint 1 종료 시(9/7) 회고에서 판정

## D-004. 분석 데이터 범위를 ① 사출성형 대회 CSV 4개로 확정

- **일자** 2026-10-04 등록 (결정은 과제해결 기간 초반)
- **상태** 확정
- **결정** 대회 데이터셋은 ① 사출성형(제품군 CN7·RG3)으로 한다. 대회가 제공한 CSV 4개(labeled·unlabeled × CN7·RG3)만 쓰고 KAMP 원본(1차 가공본)은 쓰지 않는다. CN7과 RG3는 항상 따로 실행하며, 합친 실행은 보조 분석으로도 하지 않는다.
- **배경** 대회는 공지된 데이터셋 중 팀이 1종을 골라 분석하는 방식이다. 파일은 `data/raw/injection/`에 두고 추적하지 않는다.
- **대안과 기각 사유**
  - CN7·RG3 합산 실행 — 금형이 달라 정상 범위가 다르고, 값이 파일별로 표준화돼 있으며, 불량의 성격도 다르다(CN7은 짧은 구간에 몰림, RG3는 전부 동일입력 양품 짝 보유). 기각
  - KAMP 원본 병용 — 평가 대상 범위 밖이다. 기각
- **감수한 리스크**
  1. 제품군별 불량이 17·25개뿐이다. 유효 표본은 불량 그룹 수(14·25)이고 평가 분산이 크다 → 5-fold × 10반복으로 분산을 함께 보고한다
  2. unlabeled 파일을 test로 보는 것은 가정이다(주최 측 확인 미확보)
  3. labeled와 unlabeled의 표준화 기준이 다르다 → 기록만 하고 보정하지 않는다
- **재검토 시점** 주최 측이 test 정의를 회신할 때

## D-005. 실행 환경을 conda `kamp2026`로 고정

- **일자** 2026-10-04
- **상태** 확정
- **결정** `environment.yml`로 conda 환경 `kamp2026`을 만든다. 채널은 conda-forge만 쓴다(`nodefaults`). 최상위 7개 패키지만 실제 설치 버전으로 `==` 고정한다 — python 3.11.16, numpy 2.4.6, pandas 3.0.6, scikit-learn 1.9.1, matplotlib 3.11.2, jupyter 1.1.1, pytest 9.1.1.
- **배경** 재현성 항목은 새 클론·새 환경·1회 실행으로 같은 결과가 나와야 인정된다. `environment.yml`이 이 번호를 예약해 두었다.
- **대안과 기각 사유**
  - `conda env export` 전체 고정 — Windows 빌드 문자열에 묶여 다른 OS에서 해석이 깨진다. 기각
  - 버전 미고정 — 설치 시점마다 해석 결과가 달라진다. 기각
  - defaults 채널 병용 — 설치 PC의 condarc에 따라 해석이 달라진다. 기각
- **감수한 리스크**
  1. 하위 의존성은 고정하지 않는다 → 시간이 지나면 해석 결과가 달라질 수 있다
  2. pandas 3.0은 메이저 버전이다(Copy-on-Write 기본화, 기본 문자열 dtype 변경). 2.x 기준 코드는 동작이 다를 수 있다
  3. scikit-learn 버전이 다르면 같은 seed라도 fold 배정이 기존 산출물과 다를 수 있다 → 기존 산출물과 대조할 때 버전부터 확인한다
- **재검토 시점** 파이프라인 담당의 기존 환경 버전을 받을 때

## D-006. 모델 입력을 공정변수 24개로 확정, 20개는 민감도 비교로 병기

- **일자** 2026-10-04
- **상태** 확정
- **결정** 주 입력은 ID·라벨을 뺀 공정변수 24개 전부다. 변수 목록은 설정에 따로 두지 않고 자동으로 정한다. `Plasticizing_Time`, `Plasticizing_Position`, `Cycle_Time`, `Clamp_Open_Position` 4개를 뺀 20개 결과는 민감도 비교로, 우열과 무관하게 보고서에 함께 싣는다.
- **배경** 파이프라인 담당의 사전 실험은 20개 입력이었다. 프레임워크 CV를 돌리기 전에 입력을 고정해야 했다.
- **판단 근거**
  1. 입력 자격은 "예측 시점에 쓸 수 있는가"로 판정한다. 4개 모두 최종검사 전에 기록되는 값이다
  2. "이 제품의 원인인가"는 Analyze 단계의 해석 문제지 입력 자격의 문제가 아니다
  3. 그룹 규칙(공정변수 전부 완전일치)과 기준 수치(그룹 606·591, 중복 상한 F1 0.756·0.667)가 24개 기준으로 산출됐다. 입력을 바꾸면 그룹부터 다시 검증해야 한다
- **대안과 기각 사유**
  - 20개를 주 입력 — 4개가 성형 이후 단계(계량·형개)나 사이클 전체의 값이라 이 제품의 원인으로 보기 어렵다는 근거(추정). 원인 해석에는 맞지만 예측 입력에서 뺄 근거로는 약하다. 민감도 비교로 강등
- **감수한 리스크**
  1. 등록 전에 사전 실험 결과(24개 쪽 수치 우세)를 팀이 이미 봤다. 성능은 근거로 쓰지 않았고, 20개 결과를 우열과 무관하게 병기하는 것으로 보완한다
  2. 도메인 확인 없이 리드 위임 판단으로 확정했다
  3. `Clamp_Open_Position`은 labeled에서 상수라 학습 정보가 없다. 표준편차를 쓰는 모델에서 0 나눗셈 처리가 필요하다
- **재검토 시점** 없음. 민감도 결과를 보고 주 입력을 바꾸지 않는다
